# GCC - Competition Engine

> **Status: pot allocation implemented in Phase 9; league-phase fixtures implemented in Phase 10; standings and knockout stages are still design.**
>
> `src/lib/engine/` contains the real, fully tested Phase 9 pot allocation (`random.ts`,
> `pots.ts`) and the Phase 10 fixture engine (`fixtures/`). Phase 12 implements
> standings; Phase 13 knockouts.

## 1. Principles

- **Pure TypeScript.** No database, Firebase, Next.js or environment imports. No I/O, no
  `Date.now()` inside deterministic calculations, no hidden randomness.
- **Data in, data out.** The engine receives participants, pots, format configuration,
  results and a seed; it returns fixtures, validation reports, standings and
  qualification.
- **Deterministic and reproducible.** Given the same inputs and seed, output is identical.
  Randomised draws record the seed and the generated output so a draw can be audited.
- **Independent validation.** Generation and validation are separate functions. A
  schedule is stored only after validation passes.
- **Server-only invocation.** The engine is imported by trusted server code and unit
  tests, never trusted to run from client input.

## 2. Inputs and outputs

### Pot allocation (implemented in Phase 9)

Inputs:

- The 36 registered player UIDs.
- Optional pins: `{ [uid]: 1 | 2 | 3 | 4 }` for players who must stay in a pot.
- A seed: a non-empty string generated by the server with `crypto.randomBytes`.

Outputs:

- Four pots of exactly nine, with every registered player in exactly one pot, or a
  typed error explaining why the input cannot produce a valid draw.
- A validation result listing per-pot sizes, duplicates and unknown/missing players.

The pure functions live in `src/lib/engine/pots.ts`:

```ts
shuffleIntoPots({ playerIds, locked?, seed }) -> { pots, locked }
validatePots(pots, registeredIds) -> { valid, issues[] }
```

`random.ts` implements the deterministic PRNG: a string seed is hashed with cyrb128
and expanded into a mulberry32 stream. `nextInt(n)` uses rejection sampling so every
value is uniform, and `shuffle` is a genuine Fisher-Yates shuffle. `deriveSeed(seed,
label)` returns a 32-character hex sub-seed for independently reproducible streams.
No engine module calls `Math.random`; a lint rule and a purity test enforce that
boundary.

Pins are honoured first. Locked players are placed in their pot, then the remaining
players are shuffled into the remaining capacity. A pin that overfills a pot, names
an unknown player or names the same player twice fails with a typed
`PotAllocationError` instead of silently dropping the constraint. Without pins, each
player lands in each pot with 25% probability; the unit suite checks this over 4,000
seeds with a ±3% tolerance.

### Fixture generation (implemented in Phase 10)

Inputs:

- 36 participants assigned to four pots of nine, in pot order 1–4.
- A recorded seed string generated by the server with `crypto.randomBytes`.
- Optional search budgets for tests only (`maxAttempts`, `colourNodeBudget`).

Outputs:

- 144 fixtures with matchday, home participant and away participant.
- The seed, attempt count, attempt seed and a human-readable report
  (`maxHomeAwayStreak`, `playersWithStreak3Plus`, `perMatchdayCounts`).
- A typed `FixtureGenerationError` when the pots are malformed or the bounded search
  cannot finish. A partial schedule is never returned.

The pure functions live in `src/lib/engine/fixtures/`:

```ts
generateLeaguePhase({ pots, seed }) -> { fixtures, seed, attempts, report }
validateLeaguePhase(pots, fixtures) -> { valid, errors[], stats }
```

`validateLeaguePhase` deliberately lives in `validate.ts` and imports **nothing** from
the generator or its colouring internals. It re-derives every rule from the pots and
the fixture list, so a bug shared by generation and validation cannot hide itself.

The server boundary (`src/lib/tournament/fixtures.ts`) is the only caller in
production. It generates the seed server-side, validates the output, stores the draft
and recomputes a canonical SHA-256 with `node:crypto`. The client never supplies
fixtures, tags, the seed or an algorithm version.

### Standings

Inputs:

- Participants.
- Fixtures.
- **Completed** results only. Results are entered by the tournament owner or Super Admin;
  players never submit or confirm a score.
- Format tiebreak order.

Outputs:

- Ordered table with played, won, drawn, lost, goals for/against, goal difference, points.
- Qualification outcome per participant derived from format bands.

## 3. Fixture constraints (launch format)

Every generated schedule must satisfy:

1. Exactly 36 participants, four pots of nine with unique player ids.
2. Exactly 144 matches, 18 per matchday, 8 matchdays.
3. Every participant plays exactly 8 matches and appears exactly once per matchday.
4. Every participant faces exactly 2 opponents from each pot, including their own.
5. No participant faces the same opponent twice.
6. Every participant has exactly 4 home and 4 away matches.
7. Against each pot (including their own), every participant has exactly one home and
   one away match.
8. No participant is drawn against itself.
9. Home/away runs of three or more are reduced as far as the bounded search allows;
   this is an optimisation, not a validity rule.

The independent validator returns typed codes, not strings the caller has to parse:

| Code                           | Meaning                                                     |
| ------------------------------ | ----------------------------------------------------------- |
| `pot-count-invalid`            | Not exactly four pots.                                      |
| `pot-size-invalid`             | A pot is not exactly nine players.                          |
| `player-id-invalid`            | A blank or non-string player id.                            |
| `player-duplicate`             | The same player appears in more than one pot slot.          |
| `player-count-invalid`         | Fewer than 36 unique players.                               |
| `fixture-invalid`              | A fixture is not an object.                                 |
| `match-count-invalid`          | Not exactly 144 fixtures.                                   |
| `matchday-invalid`             | A matchday outside 1–8.                                     |
| `matchday-match-count-invalid` | A matchday does not hold exactly 18 fixtures.               |
| `self-match`                   | A player drawn against themselves.                          |
| `pair-duplicate`               | The same unordered pair appears twice.                      |
| `player-unknown`               | A fixture names a player outside the confirmed pots.        |
| `matchday-player-duplicate`    | A player appears twice on one matchday.                     |
| `player-match-count-invalid`   | A player does not have exactly eight matches.               |
| `pot-opponent-count-invalid`   | A player does not face exactly two opponents from a pot.    |
| `pot-home-away-invalid`        | A player does not have one home and one away against a pot. |

The validator also returns statistics the organiser and public views can show:
`matchCount`, `perMatchdayCounts`, and per-player `home`, `away`, `homeByPot`,
`awayByPot` and `opponentsByPot`. The server stores those statistics with the draft so
a later page does not have to re-run generation to explain what was checked.

## 4. Generation approach (implemented)

### Step A — constructive pairing

Each pot becomes a seeded random ring: `ring[k]` hosts `ring[k+1]`, wrapping at nine.
Every player therefore has two within-pot matches, one at home and one away.

For every pair of pots a second seeded permutation `tau` joins the rings. At position
`a` the generator adds:

- `firstRing[a]` at home to `secondRing[tau[a]]`, and
- `secondRing[tau[a+1]]` at home to `firstRing[a]`.

There are six pot pairs and nine positions, so each pair contributes eighteen matches,
nine oriented each way. Every player meets exactly two opponents from each other pot,
one at home and one away. Together with the ring this is an 8-regular graph on 36
vertices: 36 within-pot edges and 108 cross-pot edges.

**Why the orientation is balanced.** Within a pot, the ring gives each player one
outgoing and one incoming edge. Across one pot pair, each player appears once as the
home side and once as the away side because `tau` is a bijection and the pair of
positions `a` and `a+1` covers every position exactly once. Summing over the three
other pots gives one home and one away against each pot, hence four home and four away
in total. The unit tests assert `homeByPot` and `awayByPot` are all ones.

### Step B — proper 8-edge-colouring

A schedule is exactly a proper 8-edge-colouring of the 8-regular graph: each colour is
one matchday, and every colour covers all 36 players exactly once. The engine solves
this as an exact cover with Algorithm X over a Dancing Links matrix:

- one column per edge (used exactly once),
- one column per `(player, colour)` pair (at most once),
- one row per `(edge, colour)` covering its edge column and both endpoint-colour
  columns.

The search uses minimum-remaining-values column choice and a node budget (50,000
nodes in production). If the budget is exhausted, the generator retries Step A and B
with `deriveSeed(seed, "attempt-k")`, up to 50 attempts. A total failure throws
`FixtureGenerationError("attempts-exhausted")`; no partial output is ever emitted.
The prototype achieved first-attempt colourings in 999 of 1,000 seeds at a 100,000
node budget, and the production suite completes every one of 3,000 seeds.

### Step C — best-effort streak reduction

Step C never changes a pairing. It may:

- flip the orientation of one whole block (a pot ring or one pot pair), which preserves
  one home and one away against every pot, and
- permute matchday labels.

A seeded random walk over 240 iterations accepts an improvement in
`playersWithStreak3Plus`, then in `maxHomeAwayStreak`, and sometimes accepts an equal
score to cross a plateau. The final values are reported, never treated as a validation
failure. The validator does not require a streak bound.

### Determinism and retries

For attempt 1 the attempt seed is the input seed; later attempts use
`deriveSeed(input.seed, "attempt-k")`. Every random step (ring order, pot-pair
permutations, Step C walk) derives its own labelled stream, so the same input and seed
produce byte-identical fixtures and report. A seed is recorded with the draft and the
audit log so the schedule can be replayed.

### Server boundary, draft and publication

The engine is pure; everything that touches Firestore lives in
`src/lib/tournament/fixtures.ts` and the five organiser routes under
`/api/organiser/tournaments/[id]/fixtures/`.

- **Generate** (`POST .../generate`) requires the owner or a Super Admin, a
  `pots_confirmed` tournament and a confirmed draw whose pots still validate against
  the registered field. The server creates a 32-byte seed, runs the engine, validates
  the result independently, and stores `tournaments/{id}/fixtureDrafts/current` with
  the seed, algorithm version, display fixtures, report, statistics, canonical hash,
  generator uid, timestamp and `generationCount`. Regeneration overwrites the draft
  while the tournament is still `pots_confirmed`; every generation is audited.
- **Publish** (`POST .../publish`) accepts eight optional informational
  `{ number, startsOn, endsOn }` windows. Defaults start at `startsAt`, one week apart,
  with six-day windows. Inside one transaction it re-reads the tournament, draw,
  draft and any existing match, re-runs the validator and recomputes the hash. It
  then writes 144 deterministic match documents named
  `league-md{NN}-m{NN}`, eight `matchdays/{n}` documents and 36 zeroed `standings`
  documents, and moves the tournament to `fixtures_published` with `scheduleHash`,
  `fixturesPublishedAt` and `leagueMatchesCompleted: 0`. That is 189 writes, well
  under the 500-write transaction limit. Players are notified in chunks of 18.
- **Verify** (`GET .../verify`) rebuilds the fixture list from the published matches,
  runs the same independent validator, recomputes the canonical hash and compares it
  with the tournament hash and the draft hash. It never mutates.
- **Reset** (`POST .../reset`) is allowed only while the tournament is
  `fixtures_published` or `league_phase` and no match is completed or carries a
  result. It deletes matches, matchdays and zeroed standings, restores
  `pots_confirmed`, clears the schedule fields, keeps the draft, and audits the
  reason.
- **Matchday windows** (`PATCH .../matchdays/[n]`) can be edited at any published
  stage. Windows are informational and never change a fixture or a result.

The canonical hash sorts fixtures by matchday, then home id, then away id, and hashes
newline-terminated `matchday\0homeId\0awayId` lines with SHA-256. It uses ids only, so
a display-tag correction cannot invalidate an otherwise unchanged schedule.

Visibility follows the lifecycle: a fixture draft is readable only by the owner and
the Super Admin. Matches, matchdays and standings become client-readable only once
the tournament reaches a published status. The public page and `/dashboard/fixtures`
re-check the same status server-side because the Admin SDK bypasses Security Rules.

## 6. Standings and tiebreakers

- Points: win = 3, draw = 1, loss = 0.
- Only completed results affect standings. Unplayed or corrected results are never inferred
  from client input.
- Ordering plan:
  1. Points
  2. Goal difference
  3. Goals scored
  4. Head-to-head points among tied participants
  5. Head-to-head goal difference
  6. Number of away goals scored
  7. Number of wins
  8. Deterministic final tiebreak (documented; no silent alphabet fallback)

The exact order is confirmed with the format definition in Phase 12 and documented here
before implementation. Tiebreak logic must be a pure, tested comparator with a stable
result.

## 7. Qualification bands

Positions are mapped using the format definition, not `if` statements:

| Positions | Outcome            |
| --------- | ------------------ |
| 1–8       | Round of 16        |
| 9–16      | Seeded play-offs   |
| 17–24     | Unseeded play-offs |
| 25–36     | Eliminated         |

Play-offs pair seeded teams with unseeded teams. Play-off winners join the eight direct
qualifiers to form the Round of 16.

## 8. Test plan

### Phase 9 (implemented)

- Determinism: the same seed and inputs produce identical pots.
- Seed sensitivity: different seeds produce different allocations.
- Pins: locked players keep their pot; an overfull or unknown pin fails loudly.
- Capacity and completeness: four pots of nine, every registered player exactly once.
- Validation error codes: wrong pot count, wrong pot size, duplicates, unknown and
  missing players.
- Uniformity: over 4,000 seeds with no pins, each player appears in each pot 25% ±3%.
- Purity: engine imports stay free of Firebase, Next.js, React and `Math.random`.

### Phase 10 (implemented)

`src/lib/engine/__tests__/fixtures.test.ts` runs emulator-free and covers:

- **Property validation over 3,000 seeds.** Every generated schedule passes the
  independent validator with 144 fixtures, 18 per matchday and eight matchdays. The
  measured run was average 12.08 ms, p99 28.79 ms and max 82.32 ms per generation;
  the test asserts p99 < 1,000 ms so a slow machine still has headroom.
- **Determinism.** Twenty-five seeds are generated twice and compared as serialised
  JSON, including the report. Output is byte-identical.
- **Seed diversity.** 100 seeds produce at least 99 distinct schedules.
- **Structural correctness.** Every player has four home and four away matches and
  exactly two opponents from each pot.
- **Mutation tests.** Separate corruptions prove each validator code: missing fixture
  (`match-count-invalid`), out-of-range matchday (`matchday-invalid`), self-match
  (`self-match`), repeated pair (`pair-duplicate`), unknown player (`player-unknown`),
  duplicate player on a matchday (`matchday-player-duplicate`), wrong matchday size
  (`matchday-match-count-invalid`), wrong pot opponent count
  (`pot-opponent-count-invalid`), one-sided home/away split (`pot-home-away-invalid`),
  plus pot-count, pot-size and duplicate-player cases.
- **Pair fairness over 2,000 seeds.** The same-pot pair rate measured 0.2500 (minimum
  per pair 0.2205, maximum 0.2780) against a theoretical 1/4. The cross-pot rate
  measured 0.2222 (0.1965–0.2470) against a theoretical 2/9. The test asserts a wider
  ±0.04 band so ordinary sampling variation cannot make it flaky.
- **Typed failure.** A zero node budget with one attempt throws
  `FixtureGenerationError("attempts-exhausted")`, and an odd cycle is reported as
  uncolourable by a separate 2-colour test. No partial schedule is produced.
- **Purity.** The purity test includes every fixture engine file and forbids
  `Math.random`, Firebase, Next.js, Node built-ins and `server-only`.

Emulator-backed integration tests (`tests/integration/fixtures.test.ts`) prove the
server boundary: generation needs a confirmed draw; publication writes exactly 144
matches, eight matchdays and 36 zeroed standings; two concurrent publishes leave one
set; tampering makes verification fail and produces a different hash; reset works
before a result and is refused afterwards; the public loader returns nothing before
publication and 144 fixtures afterwards; another organiser gets 404 and a plain player
gets 403. Rules tests prove a fixture draft never leaks to a signed-in player or an
anonymous reader, and that matchday windows are visible only while the tournament is
published.

### Later stages

- Standings: only confirmed results count; ordering is stable under ties.
- Qualification: band boundaries (8/9, 16/17, 24/25) map correctly.
- Knockout: bracket progression and winner propagation.

## 9. Interface discipline

The engine may depend on its own `types.ts` and on plain configuration objects passed in.
It must not import from `src/lib/firebase`, `next/*`, `react` or `process.env`. This is
enforced by review and, from Phase 18, by a lint rule.
