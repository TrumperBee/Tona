# GCC - Competition Engine

> **Status: pot allocation implemented in Phase 9; league-phase fixtures implemented in Phase 10; results and result reports implemented in Phase 11; league standings and tie-breakers implemented in Phase 12; knockout stages, seeded draws and tournament completion implemented in Phase 13.**
>
> `src/lib/engine/` contains the real, fully tested Phase 9 pot allocation (`random.ts`,
> `pots.ts`), the Phase 10 fixture engine (`fixtures/`), the Phase 12 standings engine
> (`standings/`) and the Phase 13 knockout engine (`knockout/`).

## 1. Principles

- **Pure TypeScript.** No database, Firebase, Next.js or environment imports. No I/O, no
  `Date.now()` inside deterministic calculations, no hidden randomness.
- **Data in, data out.** The engine receives participants, pots, format configuration,
  results and a seed; it returns fixtures, validation reports, standings and
  qualification.
- **Deterministic and reproducible.** Given the same inputs and seed, output is identical.
  Randomised draws record the seed and the generated output so a draw can be audited.
- **Independent validation.** Generation and validation are separate functions. A
  schedule is stored only after validation passes.
- **Server-only invocation.** The engine is imported by trusted server code and unit
  tests, never trusted to run from client input.

## 2. Inputs and outputs

### Pot allocation (implemented in Phase 9)

Inputs:

- The 36 registered player UIDs.
- Optional pins: `{ [uid]: 1 | 2 | 3 | 4 }` for players who must stay in a pot.
- A seed: a non-empty string generated by the server with `crypto.randomBytes`.

Outputs:

- Four pots of exactly nine, with every registered player in exactly one pot, or a
  typed error explaining why the input cannot produce a valid draw.
- A validation result listing per-pot sizes, duplicates and unknown/missing players.

The pure functions live in `src/lib/engine/pots.ts`:

```ts
shuffleIntoPots({ playerIds, locked?, seed }) -> { pots, locked }
validatePots(pots, registeredIds) -> { valid, issues[] }
```

`random.ts` implements the deterministic PRNG: a string seed is hashed with cyrb128
and expanded into a mulberry32 stream. `nextInt(n)` uses rejection sampling so every
value is uniform, and `shuffle` is a genuine Fisher-Yates shuffle. `deriveSeed(seed,
label)` returns a 32-character hex sub-seed for independently reproducible streams.
No engine module calls `Math.random`; a lint rule and a purity test enforce that
boundary.

Pins are honoured first. Locked players are placed in their pot, then the remaining
players are shuffled into the remaining capacity. A pin that overfills a pot, names
an unknown player or names the same player twice fails with a typed
`PotAllocationError` instead of silently dropping the constraint. Without pins, each
player lands in each pot with 25% probability; the unit suite checks this over 4,000
seeds with a ±3% tolerance.

### Fixture generation (implemented in Phase 10)

Inputs:

- 36 participants assigned to four pots of nine, in pot order 1–4.
- A recorded seed string generated by the server with `crypto.randomBytes`.
- Optional search budgets for tests only (`maxAttempts`, `colourNodeBudget`).

Outputs:

- 144 fixtures with matchday, home participant and away participant.
- The seed, attempt count, attempt seed and a human-readable report
  (`maxHomeAwayStreak`, `playersWithStreak3Plus`, `perMatchdayCounts`).
- A typed `FixtureGenerationError` when the pots are malformed or the bounded search
  cannot finish. A partial schedule is never returned.

The pure functions live in `src/lib/engine/fixtures/`:

```ts
generateLeaguePhase({ pots, seed }) -> { fixtures, seed, attempts, report }
validateLeaguePhase(pots, fixtures) -> { valid, errors[], stats }
```

`validateLeaguePhase` deliberately lives in `validate.ts` and imports **nothing** from
the generator or its colouring internals. It re-derives every rule from the pots and
the fixture list, so a bug shared by generation and validation cannot hide itself.

The server boundary (`src/lib/tournament/fixtures.ts`) is the only caller in
production. It generates the seed server-side, validates the output, stores the draft
and recomputes a canonical SHA-256 with `node:crypto`. The client never supplies
fixtures, tags, the seed or an algorithm version.

### Result recording (implemented in Phase 11)

Results are administrative facts, not engine output. The tournament owner or a
Super Admin records a final score after the match; players never submit or
confirm one. The pure transition rules live in
`src/lib/tournament/result-state.ts`:

```ts
planResultTransition("enter" | "correct" | "clear", { stage, status, hasResult });
```

Only the league stage is handled by the league result module. Knockout legs are
dispatched to `src/lib/tournament/knockout-results.ts` (Phase 13), which recomputes
the tie and never rebuilds league standings. For league matches, entering needs a
`scheduled` match with no result and produces `completed`; correcting and clearing
need a `completed` match with a result. Clearing produces `scheduled`. The server
boundary (`src/lib/tournament/results.ts`) applies the plan inside one Firestore
transaction per action, updates `leagueMatchesCompleted`, and moves the
tournament between `fixtures_published` and `league_phase`. Bulk entry performs
the same checks for up to 18 matches in one all-or-nothing transaction and
refuses knockout matches.

Every enter/bulk/correct/clear also rebuilds the complete league table inside the
same transaction (Phase 12). All reads happen first — tournament, draw,
registrations and all matches — because Firestore requires reads before writes.
The pending result change is applied in memory, the pure engine computes the
table, and the match, all standing documents and the tournament counters are then
written together. Bulk entry computes once for the whole batch; the transaction
reads at most 144 match documents and writes 36 standing documents, staying far
below the 500-write limit. A committed result and its table can therefore never
disagree, and a failed transaction leaves the previous table untouched. After
publication the same path writes 36 zero-match rows from the confirmed draw, so
the Table tab exists before the first result without inventing a score.

### Standings (implemented in Phase 12)

Standings are derived data. There is no manual table row and no client write: every
value comes from the entered players and the recorded, completed league results. The
pure engine lives in `src/lib/engine/standings/`:

```ts
computeStandings({ players: { id, lot }[], matches, profile? }) -> StandingRow[]
assignBands(rows) -> StandingRow[]
compareStandingRows(a, b, profile) -> number
deriveLot(tiebreakSeed, participantId) -> number
```

Inputs:

- The confirmed field (36 players) and their deterministic `lot`.
- **Completed** league results only. Unplayed fixtures and cleared results never
  contribute; no score is inferred from client input.
- The tournament's tie-break profile (`uefa`, the default, or `classic`).

Outputs:

- One row per player with played, won, drawn, lost, goals for/against, goal
  difference, points, away goals, wins, away wins and the last five results.
- Opponents' aggregate points, goal difference and goals scored.
- Position 1..N, the qualification band and — for a row tied on points with the row
  above — the first criterion that separated them (`separatedBy`).

The server boundary (`src/lib/tournament/standings.ts`) supplies identities from the
draw snapshot (falling back to registrations, then match participants), derives each
lot from the draw's stored `tiebreakSeed`, and writes the `standings/{uid}` documents.
The seed fallback for a legacy tournament without a draw is `standings:{tournamentId}`,
so the table is still reproducible. The profile may be changed only while
`leagueMatchesCompleted` is zero; the PATCH transaction locks it after the first
result, because the stored table was built with that profile.

Two guarded routes exist for repair, never for editing a table row:

- `POST /api/organiser/tournaments/[id]/standings/recalculate` rebuilds every row from
  recorded results and audits the repair.
- `GET /api/organiser/tournaments/[id]/standings/verify` recomputes the table and
  compares every stored field. It reports additions, removals and mismatches without
  mutating anything.

`standingsUpdatedAt` on the tournament records the last rebuild. A row is
`provisional` until all 144 league matches are recorded.

## 3. Fixture constraints (launch format)

Every generated schedule must satisfy:

1. Exactly 36 participants, four pots of nine with unique player ids.
2. Exactly 144 matches, 18 per matchday, 8 matchdays.
3. Every participant plays exactly 8 matches and appears exactly once per matchday.
4. Every participant faces exactly 2 opponents from each pot, including their own.
5. No participant faces the same opponent twice.
6. Every participant has exactly 4 home and 4 away matches.
7. Against each pot (including their own), every participant has exactly one home and
   one away match.
8. No participant is drawn against itself.
9. Home/away runs of three or more are reduced as far as the bounded search allows;
   this is an optimisation, not a validity rule.

The independent validator returns typed codes, not strings the caller has to parse:

| Code                           | Meaning                                                     |
| ------------------------------ | ----------------------------------------------------------- |
| `pot-count-invalid`            | Not exactly four pots.                                      |
| `pot-size-invalid`             | A pot is not exactly nine players.                          |
| `player-id-invalid`            | A blank or non-string player id.                            |
| `player-duplicate`             | The same player appears in more than one pot slot.          |
| `player-count-invalid`         | Fewer than 36 unique players.                               |
| `fixture-invalid`              | A fixture is not an object.                                 |
| `match-count-invalid`          | Not exactly 144 fixtures.                                   |
| `matchday-invalid`             | A matchday outside 1–8.                                     |
| `matchday-match-count-invalid` | A matchday does not hold exactly 18 fixtures.               |
| `self-match`                   | A player drawn against themselves.                          |
| `pair-duplicate`               | The same unordered pair appears twice.                      |
| `player-unknown`               | A fixture names a player outside the confirmed pots.        |
| `matchday-player-duplicate`    | A player appears twice on one matchday.                     |
| `player-match-count-invalid`   | A player does not have exactly eight matches.               |
| `pot-opponent-count-invalid`   | A player does not face exactly two opponents from a pot.    |
| `pot-home-away-invalid`        | A player does not have one home and one away against a pot. |

The validator also returns statistics the organiser and public views can show:
`matchCount`, `perMatchdayCounts`, and per-player `home`, `away`, `homeByPot`,
`awayByPot` and `opponentsByPot`. The server stores those statistics with the draft so
a later page does not have to re-run generation to explain what was checked.

## 4. Generation approach (implemented)

### Step A — constructive pairing

Each pot becomes a seeded random ring: `ring[k]` hosts `ring[k+1]`, wrapping at nine.
Every player therefore has two within-pot matches, one at home and one away.

For every pair of pots a second seeded permutation `tau` joins the rings. At position
`a` the generator adds:

- `firstRing[a]` at home to `secondRing[tau[a]]`, and
- `secondRing[tau[a+1]]` at home to `firstRing[a]`.

There are six pot pairs and nine positions, so each pair contributes eighteen matches,
nine oriented each way. Every player meets exactly two opponents from each other pot,
one at home and one away. Together with the ring this is an 8-regular graph on 36
vertices: 36 within-pot edges and 108 cross-pot edges.

**Why the orientation is balanced.** Within a pot, the ring gives each player one
outgoing and one incoming edge. Across one pot pair, each player appears once as the
home side and once as the away side because `tau` is a bijection and the pair of
positions `a` and `a+1` covers every position exactly once. Summing over the three
other pots gives one home and one away against each pot, hence four home and four away
in total. The unit tests assert `homeByPot` and `awayByPot` are all ones.

### Step B — proper 8-edge-colouring

A schedule is exactly a proper 8-edge-colouring of the 8-regular graph: each colour is
one matchday, and every colour covers all 36 players exactly once. The engine solves
this as an exact cover with Algorithm X over a Dancing Links matrix:

- one column per edge (used exactly once),
- one column per `(player, colour)` pair (at most once),
- one row per `(edge, colour)` covering its edge column and both endpoint-colour
  columns.

The search uses minimum-remaining-values column choice and a node budget (50,000
nodes in production). If the budget is exhausted, the generator retries Step A and B
with `deriveSeed(seed, "attempt-k")`, up to 50 attempts. A total failure throws
`FixtureGenerationError("attempts-exhausted")`; no partial output is ever emitted.
The prototype achieved first-attempt colourings in 999 of 1,000 seeds at a 100,000
node budget, and the production suite completes every one of 3,000 seeds.

### Step C — best-effort streak reduction

Step C never changes a pairing. It may:

- flip the orientation of one whole block (a pot ring or one pot pair), which preserves
  one home and one away against every pot, and
- permute matchday labels.

A seeded random walk over 240 iterations accepts an improvement in
`playersWithStreak3Plus`, then in `maxHomeAwayStreak`, and sometimes accepts an equal
score to cross a plateau. The final values are reported, never treated as a validation
failure. The validator does not require a streak bound.

### Determinism and retries

For attempt 1 the attempt seed is the input seed; later attempts use
`deriveSeed(input.seed, "attempt-k")`. Every random step (ring order, pot-pair
permutations, Step C walk) derives its own labelled stream, so the same input and seed
produce byte-identical fixtures and report. A seed is recorded with the draft and the
audit log so the schedule can be replayed.

### Server boundary, draft and publication

The engine is pure; everything that touches Firestore lives in
`src/lib/tournament/fixtures.ts` and the five organiser routes under
`/api/organiser/tournaments/[id]/fixtures/`.

- **Generate** (`POST .../generate`) requires the owner or a Super Admin, a
  `pots_confirmed` tournament and a confirmed draw whose pots still validate against
  the registered field. The server creates a 32-byte seed, runs the engine, validates
  the result independently, and stores `tournaments/{id}/fixtureDrafts/current` with
  the seed, algorithm version, display fixtures, report, statistics, canonical hash,
  generator uid, timestamp and `generationCount`. Regeneration overwrites the draft
  while the tournament is still `pots_confirmed`; every generation is audited.
- **Publish** (`POST .../publish`) accepts eight optional informational
  `{ number, startsOn, endsOn }` windows. Defaults start at `startsAt`, one week apart,
  with six-day windows. Inside one transaction it re-reads the tournament, draw,
  draft and any existing match, re-runs the validator and recomputes the hash. It
  then writes 144 deterministic match documents named
  `league-md{NN}-m{NN}`, eight `matchdays/{n}` documents and 36 zeroed `standings`
  documents, and moves the tournament to `fixtures_published` with `scheduleHash`,
  `fixturesPublishedAt` and `leagueMatchesCompleted: 0`. That is 189 writes, well
  under the 500-write transaction limit. Players are notified in chunks of 18.
- **Verify** (`GET .../verify`) rebuilds the fixture list from the published matches,
  runs the same independent validator, recomputes the canonical hash and compares it
  with the tournament hash and the draft hash. It never mutates.
- **Reset** (`POST .../reset`) is allowed only while the tournament is
  `fixtures_published` or `league_phase` and no match is completed or carries a
  result. It deletes matches, matchdays and zeroed standings, restores
  `pots_confirmed`, clears the schedule fields, keeps the draft, and audits the
  reason.
- **Matchday windows** (`PATCH .../matchdays/[n]`) can be edited at any published
  stage. Windows are informational and never change a fixture or a result.

The canonical hash sorts fixtures by matchday, then home id, then away id, and hashes
newline-terminated `matchday\0homeId\0awayId` lines with SHA-256. It uses ids only, so
a display-tag correction cannot invalidate an otherwise unchanged schedule.

Visibility follows the lifecycle: a fixture draft is readable only by the owner and
the Super Admin. Matches, matchdays and standings become client-readable only once
the tournament reaches a published status. The public page and `/dashboard/fixtures`
re-check the same status server-side because the Admin SDK bypasses Security Rules.

## 5. Knockout stages (implemented in Phase 13)

The knockout bracket is **defined by this platform**. It is inspired by the modern
36-team European format but it is not an exact copy of UEFA's path, and the product
never claims that it is.

### 5.1 Bracket definition

After the league phase closes, positions 1–8 go directly to the Round of 16 and
positions 9–24 enter the knockout play-off. Positions 25–36 are eliminated.

Play-off groups (the draw is random within each group, always one seeded player
against one unseeded player):

| Group | Seeded | Unseeded |
| ----- | ------ | -------- |
| A     | 9, 10  | 23, 24   |
| B     | 11, 12 | 21, 22   |
| C     | 13, 14 | 19, 20   |
| D     | 15, 16 | 17, 18   |

Each group produces two ties, so the play-off has eight ties and sixteen legs by
default.

The Round of 16 places the direct qualifiers against the play-off winners in the
fixed order `[1, 8, 4, 5, 2, 7, 3, 6]`. Within each qualifying pair the two group
winners are assigned randomly:

- group D winners vs seeds 1 and 2,
- group C winners vs seeds 3 and 4,
- group B winners vs seeds 5 and 6,
- group A winners vs seeds 7 and 8.

Because of that order, seeds 1 and 2 are always on opposite halves and can only meet
in the final. Quarter-finals pair adjacent Round-of-16 bracket slots, and
semi-finals pair adjacent quarter-final slots. The final is always one match.

Home advantage in a two-legged tie: the lower-ranked player hosts leg 1 and the
higher-ranked player hosts leg 2. A single leg or the final lists the higher-ranked
player first.

One organiser action chooses the leg count for every round before the final. The
choice is stored once as `knockoutLegs` (1 or 2, default 2), so every play-off,
Round-of-16, quarter-final and semi-final tie uses it; the final is always one match.
There is **no away-goals rule**. A tie level on aggregate after every leg is stored
as `needs_decider` and the organiser records the winner, the method (`extra_time` or
`penalties`), an optional note and, for penalties, a consistent penalty score.

### 5.2 Pure engine

`src/lib/engine/knockout/` is pure TypeScript and imports only its own types and the
shared seeded PRNG (`../random`):

```ts
buildKnockoutBracket({ standings, seed, legs }) -> KnockoutBracket
resolveBracket(bracket) -> KnockoutBracket
advanceBracket(bracket, { tieId, winner }) -> KnockoutBracket
dependentTieIds(bracket, tieId) -> Set<string>
homeUidForLeg(tie, leg) -> string
resolveTie(tie, matches) -> TieResolution
applyDecider(resolution, tie, decider) -> TieResolution
validateBracket(bracket) -> { valid, issues[] }
```

`buildKnockoutBracket` builds the whole tree at once. Every random choice is made
there: which unseeded player meets which seeded player inside a play-off group, and
which of the two group winners meets which direct seed in the Round of 16.
Quarter-final, semi-final and final slots are fixed adjacent-slot progressions. They
hold a `KnockoutSlot` reference, either `{ type: "seed", seed }` or
`{ type: "winnerOf", tieId }`, plus the known participant (or `null`).

The structural `higher` and `lower` slots are the top and bottom source of a tie,
not a ranking. In the play-offs and Round of 16 the higher slot is the better seed;
in later rounds the better-ranked participant is derived when the tie resolves.
`resolveBracket` recomputes every participant and winner from the references alone,
so a changed earlier result can never leak into a later round. `advanceBracket`
applies one tie result and resolves the whole tree; applying a winner who is not a
participant is refused.

The independent validator re-derives counts, bracket slots, unique participants,
seeded/unseeded group pairing, direct-qualifier placement, seeds 1/2 separation, the
adjacent-slot path and every slot reference. Generation and validation live in
separate modules, so a generator bug cannot silently validate itself.

A stored tie carries the `higher` and `lower` slot documents (`ref`, `uid`,
`gamerTag`, `position`), the leg count, status, aggregate, legs played, winner and
position, `decidedBy`, decider note and penalty score. The final is always one leg.
Randomness comes only from the server seed; the client never supplies a tie, seed,
participant or match id.

### 5.3 Data and routes

- `tournaments/{id}/knockoutTies/{tieId}` - server-written, public-read once the
  tournament is in a knockout/public status. It carries the tie id, round, bracket
  slot, leg count, the two slot documents (`ref`, `uid`, `gamerTag`, `position`),
  group, aggregate keyed by the structural higher/lower slot, legs played, status,
  winner and position, `decidedBy`, decider note and penalty score.
- `tournaments/{id}/matches/{tieId}-l{leg}` - normal match documents with
  `stage: playoff | r16 | qf | sf | final`, `matchday: 0`, `scheduledAt: null`,
  `tieId` and `leg`. Existing result entry, notifications, match pages and history
  work unchanged.
- Tournament fields: `leaguePhaseClosedAt`, `knockoutLegs`, `knockoutSeed`,
  `knockoutAlgorithmVersion`, `knockoutBracketHash`, `knockoutGeneratedAt`,
  `championUid`, `runnerUpUid`, `completedAt`.

Routes under `/api/organiser/tournaments/[id]/knockout/`:

| Route                      | Purpose                                                                                                                                                                                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST generate`            | The one setup action. Requires all 144 league results and `league_phase`; freezes the table, draws, validates and writes all 23 ties and the initially playable matches, stores seed/legs/hash, notifies all 36 players and audit-logs. A second call returns the stored summary without writing. |
| `POST reset`               | Body `{ reason }`. Allowed only while no knockout tie or leg has a result; deletes the 23 ties and every knockout match and returns the tournament to `league_phase`.                                                                                                                             |
| `POST ties/[tieId]/decide` | Records the extra-time/penalty decider for a level tie and advances the winner in the same transaction.                                                                                                                                                                                           |

Result entry and correction are shared with Phase 11. For knockout legs the server
dispatches to `knockout-results.ts`. Every enter/correct/clear reads the tournament,
all ties and all matches in one transaction, resolves the affected tie and writes its
winner into every dependent slot. A dependent tie whose two sides are now known gets
its leg matches created automatically (one or two legs by `knockoutLegs`, the final
always one). Correcting or clearing is refused while any transitively dependent tie
already holds a result, and the message names that tie. A changed winner deletes and
rebuilds dependent matches that have no result. Bulk entry accepts league matches only.
Completing the final sets `championUid`, `runnerUpUid`, `completedAt` and status
`completed` inside the same transaction, then notifies everyone. There is no manual
complete step.

### 5.4 Frozen league table

Generating the knockout stage is the freeze point. That transaction reads the
tournament and all matches, requires exactly 144 completed league matches, rebuilds
the table from those results, sets `provisional: false` on every standing, and moves
the tournament to `knockout` with `leaguePhaseClosedAt`. From then on, knockout
results never call the standings builder. The stored table, its positions, bands and
tie-break explanations remain exactly as they were at generation, and tournament
completion only writes the champion, runner-up, `completedAt`, status and membership
status.

### 5.5 UI

- **Organiser Knockout tab** - before generation it shows the progress
  (`n/144` league results) and a "Generate knockout stage" card. The dialog chooses
  one or two legs for every round before the final and summarises who qualifies
  (top 8 direct, 9-24 play-offs, 25-36 eliminated). After generation the tab renders
  the same bracket as the public page plus a list grouped by round. Tapping a tie
  opens a bottom sheet with both players, the legs, inline score inputs that save in
  place without a page jump, the decider dialog when needed, a "Waiting for
  {Winner of P4}" state, and the reset action (dialog with a reason) when no knockout
  result exists.
- **Public knockout page** on `/tournaments/[slug]/knockout` (also the tournament
  Knockout tab) - a visual bracket with Play-offs, Round of 16, Quarter-finals,
  Semi-finals and Final columns joined by CSS connectors. Placeholders show
  "Seed 3" or "Winner of P4" and fill automatically as results arrive; completed
  ties show the aggregate and highlight the winner; the champion appears in a
  banner. On mobile the bracket scrolls horizontally with scroll-snap, round chips
  jump to a round, a Bracket/List toggle switches layout, and tapping a tie opens a
  leg-detail sheet. Every value is stored data and the empty state is honest before
  generation.
- **Player dashboard** - knockout status per tournament (direct qualifier,
  play-off, eliminated, still in the bracket, runner-up or champion), the aggregate
  of the latest tie and the next leg once its opponent is decided.

### 5.6 Tests for Phase 13

`src/lib/engine/__tests__/knockout.test.ts` runs emulator-free and covers:

- determinism for a recorded seed and variation between seeds;
- 2,000-seed property tests that every generated bracket passes the independent
  validator, has 23 resolvable ties and never brings seeds 1 and 2 together before
  the final;
- that every player appears exactly once in the first knockout round they enter and
  that every play-off pairs one seeded with one unseeded player;
- fairness: within each play-off group every unseeded player faces each seeded player
  with probability 1/2 ±0.05 over 2,000 seeds;
- every `resolveTie` outcome: aggregate win, level after two legs needing a decider,
  extra time, penalties, single leg and cleared/unplayed legs;
- mutation tests for every validator code and bracket-path validation from R16 to
  the final.

Emulator-backed integration tests (`tests/integration/knockout.test.ts`) prove the
server boundary. Two whole simulations build a 36-player competition - shuffled
draw, 144 entered results, one generate action, every knockout round including a
penalty decider, and automatic completion - once with two legs and once with one,
and assert the champion, runner-up, a completed 23-tie bracket with the expected 45
or 23 knockout matches, a single-leg final, all 36 non-provisional standing rows and
a league table identical to the one frozen at generation. Further cases prove that
generation is refused while a league result is missing, that it freezes the table,
writes all 23 ties and notifies all 36 players once, that a second generate call
returns the stored bracket without writing, and that the final stays one match when
the bracket uses two legs. They also prove dependent matches are created only when
both sides are known, that a correction is refused (naming the blocking tie) once a
dependent tie has a result, that a changed winner propagates into the next round and
rebuilds its untouched matches, that a level single leg needs an explicit penalties
decider, that reset deletes an unplayed bracket and returns to `league_phase`, that
reset is refused after any result, and that another organiser gets 404 while a player
gets 403. Rules tests keep `knockoutTies` owner-readable before publication and
publicly readable once the tournament is published, and never expose draft data.

The same end-to-end runner is exposed as `npm run simulate`. It starts the emulators,
builds a complete tournament through the real routes and prints the champion,
runner-up, per-round tie/match/decider counts and whether the league table stayed
frozen.

## 6. Standings and tiebreakers

- Points: win = 3, draw = 1, loss = 0.
- Only completed results affect standings. Unplayed or cleared results never contribute,
  and no result is inferred from client input.
- The table is one sequential sort over the whole field, never a set of head-to-head
  mini-leagues. Higher values rank first for every criterion except the lot, which ranks
  ascending. A final participant-id comparison keeps the order strict even if two lots
  collide.
- The `uefa` profile (default) applies, in order:
  1. Points
  2. Goal difference
  3. Goals scored
  4. Away goals scored
  5. Wins
  6. Away wins
  7. Opponents' aggregate points
  8. Opponents' aggregate goal difference
  9. Opponents' aggregate goals scored
  10. Drawing of lots
- The `classic` profile applies points, goal difference, goals scored, wins, then the
  drawing of lots. It ignores the away and opponent aggregates.
- **The lot is deterministic.** `deriveLot(tiebreakSeed, uid)` hashes the draw's stored
  tie-break seed and the player id into a safe 53-bit integer. The same tournament and
  field always produce the same lot order; input array order is never consulted. There is
  no alphabetical or manual fallback.
- `separatedBy` on each row records the first criterion that separated it from the row
  above when the two are level on points. The public and organiser tables use it to
  explain why positions differ, and every table shows the active profile's full criterion
  order.

## 7. Qualification bands

Positions are mapped by `assignBands`, using the format definition rather than scattered
conditionals:

| Positions | Outcome            |
| --------- | ------------------ |
| 1–8       | Round of 16        |
| 9–16      | Seeded play-offs   |
| 17–24     | Unseeded play-offs |
| 25–36     | Eliminated         |

Play-offs pair seeded teams with unseeded teams. Play-off winners join the eight direct
qualifiers to form the Round of 16.

## 8. Test plan

### Phase 9 (implemented)

- Determinism: the same seed and inputs produce identical pots.
- Seed sensitivity: different seeds produce different allocations.
- Pins: locked players keep their pot; an overfull or unknown pin fails loudly.
- Capacity and completeness: four pots of nine, every registered player exactly once.
- Validation error codes: wrong pot count, wrong pot size, duplicates, unknown and
  missing players.
- Uniformity: over 4,000 seeds with no pins, each player appears in each pot 25% ±3%.
- Purity: engine imports stay free of Firebase, Next.js, React and `Math.random`.

### Phase 10 (implemented)

`src/lib/engine/__tests__/fixtures.test.ts` runs emulator-free and covers:

- **Property validation over 3,000 seeds.** Every generated schedule passes the
  independent validator with 144 fixtures, 18 per matchday and eight matchdays. The
  measured run was average 12.08 ms, p99 28.79 ms and max 82.32 ms per generation;
  the test asserts p99 < 1,000 ms so a slow machine still has headroom.
- **Determinism.** Twenty-five seeds are generated twice and compared as serialised
  JSON, including the report. Output is byte-identical.
- **Seed diversity.** 100 seeds produce at least 99 distinct schedules.
- **Structural correctness.** Every player has four home and four away matches and
  exactly two opponents from each pot.
- **Mutation tests.** Separate corruptions prove each validator code: missing fixture
  (`match-count-invalid`), out-of-range matchday (`matchday-invalid`), self-match
  (`self-match`), repeated pair (`pair-duplicate`), unknown player (`player-unknown`),
  duplicate player on a matchday (`matchday-player-duplicate`), wrong matchday size
  (`matchday-match-count-invalid`), wrong pot opponent count
  (`pot-opponent-count-invalid`), one-sided home/away split (`pot-home-away-invalid`),
  plus pot-count, pot-size and duplicate-player cases.
- **Pair fairness over 2,000 seeds.** The same-pot pair rate measured 0.2500 (minimum
  per pair 0.2205, maximum 0.2780) against a theoretical 1/4. The cross-pot rate
  measured 0.2222 (0.1965–0.2470) against a theoretical 2/9. The test asserts a wider
  ±0.04 band so ordinary sampling variation cannot make it flaky.
- **Typed failure.** A zero node budget with one attempt throws
  `FixtureGenerationError("attempts-exhausted")`, and an odd cycle is reported as
  uncolourable by a separate 2-colour test. No partial schedule is produced.
- **Purity.** The purity test includes every fixture engine file and forbids
  `Math.random`, Firebase, Next.js, Node built-ins and `server-only`.

Emulator-backed integration tests (`tests/integration/fixtures.test.ts`) prove the
server boundary: generation needs a confirmed draw; publication writes exactly 144
matches, eight matchdays and 36 zeroed standings; two concurrent publishes leave one
set; tampering makes verification fail and produces a different hash; reset works
before a result and is refused afterwards; the public loader returns nothing before
publication and 144 fixtures afterwards; another organiser gets 404 and a plain player
gets 403. Rules tests prove a fixture draft never leaks to a signed-in player or an
anonymous reader, and that matchday windows are visible only while the tournament is
published.

### Phase 11 (implemented)

`src/lib/tournament/result-state.test.ts` and
`src/lib/validation/match.test.ts` cover the pure transition rules and every
input schema (scores 0–99, bulk maximum 18, correction/clear reason 5–300,
report reason 10–500, resolution note 5–300, unknown fields rejected).

Emulator-backed integration tests (`tests/integration/results.test.ts`) prove the
server boundary: entry writes the match, the completed counter and
`league_phase` together; a second entry is rejected with a correction hint; two
concurrent entries leave exactly one success and one 409; entry before
publication is refused; corrections and clears require a reason and produce an
audit entry with before/after values; clearing the last result returns the
tournament to `fixtures_published`; bulk entry is all-or-nothing; another
organiser gets 404 and a plain player gets 403; a Super Admin can act on any
tournament; both players are notified with the recorded score; and result
reports are participant-only, one open per player per match, resolved with a
required note by the owner or Super Admin, with an audit entry and reporter
notification.

### Phase 12 (implemented)

`src/lib/engine/__tests__/standings.test.ts` runs emulator-free and contains 25 tests:

- **Hand-computed tables.** Played/won/drawn/lost, goals, away goals, points, form and
  positions; last-five form with the newest last; a zero-match 36-player table ordered
  by lot regardless of input order.
- **One test per tie-break criterion.** Each synthetic comparison deliberately ties every
  earlier criterion, then proves the named one decides: points, goal difference, goals
  scored, away goals, wins, away wins, opponents' aggregate points, opponents' aggregate
  goal difference, opponents' aggregate goals, and the lot. A separate test proves the
  classic profile ignores away/opponent criteria.
- **Worked criterion-5+ tables.** A one-win team with three draws and a two-win team both
  finish on 6 points, GF 2, GA 0, GD 2, 0 away goals: criterion 5 (wins) puts the two-win
  team above, and the other row records `separatedBy: "wins"`. Further worked tables
  resolve equal records by away wins (criterion 6), opponents' aggregate points
  (criterion 7: 6 vs 3), opponents' aggregate goal difference (criterion 8: 1 vs 0) and
  opponents' aggregate goals (criterion 9: 4 vs 3).
- **Qualification bands.** Exactly 8 direct, 8 seeded play-off, 8 unseeded play-off and
  12 eliminated positions, with the 8/9, 16/17 and 24/25 boundaries correct.
- **1,000-run property test.** Each run builds 36 players and 144 random complete results.
  It asserts: the table is identical when both players and matches are shuffled; repeated
  computation is identical; positions are 1..36 and every adjacent pair is strictly
  ordered under the comparator; total points equal three per decisive match plus two per
  draw; goals for equal goals against; and each row's played, points, goal difference and
  all three opponent aggregates equal a brute-force recount over the raw matches.
- **Purity.** The purity test now includes every standings engine file.

Emulator-backed integration tests (`tests/integration/results.test.ts`) prove the server
boundary: entry writes the match and the derived table in one transaction and a fresh
verification matches all stored rows; correction moves the positions; clearing returns
every row to zero and restores `fixtures_published`; a bulk batch recomputes once and
verifies; two concurrent entries leave one success and a table consistent with the
committed score; a manually corrupted row is reported by verify and repaired by the
audited recalculate action; the tie-break profile can change before the first result and
is refused with 403 afterwards; and another organiser gets 404 while a plain player gets
403 for both repair routes. The fixture integration test also proves publication writes
36 zero-match rows with positions 1..36, distinct lots and the 8/8/8/12 band split.

## 9. Interface discipline

The engine may depend on its own `types.ts` and on plain configuration objects passed in.
It must not import from `src/lib/firebase`, `next/*`, `react` or `process.env`. This is
enforced by review and, from Phase 18, by a lint rule.
